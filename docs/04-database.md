# База данных (PostgreSQL + pgvector)

## Цель

Храним чанки документов вместе с их векторными представлениями и обеспечиваем быстрый семантический поиск

*В архитектуре у нас  PostgreSQL + pgvector используется как альтернатива backend векторного хранилища (по умолчанию - Chroma). Надо чтобы сравнивать подходы в рамках экспериментов

Разваорачиваем через Docker ([см. docker-compose.yml](docker-compose.yml))


## Выбор индекса

В `pgvector` основные варианты это HNSW и IVFFlat

**Как работают**

**HNSW:** Строит многоуровневый граф. Поиск начинается с верхних «грубых» слоёв и постепенно спускается к более точным. Благодаря этому обычно получается хороший баланс скорости и качества

**IVFFlat:** Сначала все векторы разбиваются на кластеры (списки). При поиске алгоритм смотрит только в несколько ближайших к запросу кластеров. Чем лучше подобрано число кластеров (`lists`), тем лучше результат

Почему выбран HNSW

1. Объём данных небольшой. Локальная база знаний на ноутбуке - это тысячи / десятки тысяч чанков. На таких объёмах HNSW показывает себя стабильно хорошо

2. Проще в использовании. Меньше параметров, которые нужно подбирать

3. Лучше качество поиска по умолчанию. Для RAG важнее найти релевантные чанки, чем выжать максимум скорости. HNSW обычно даёт более высокий recall

4. Хорошо работает с cosine distance. Мы используем оператор `<=>` (cosine distance) и класс операторов `vector_cosine_ops` - это стандартный вариант для текстовых эмбеддингов


Пример создания IVFFlat-индекса (если потом захочется добавить в эксперимент экспериментов):

```sql
CREATE INDEX documents_embedding_ivfflat_idx
    ON documents
    USING ivfflat (embedding vector_cosine_ops)
    WITH (lists = 100);   -- rough rule: rows / 1000
